# Expert Hardware Kuwait — Project Notes

Static e-commerce site for a Kuwait hardware store, hosted on GitHub Pages, backed by Supabase. No build step, no `package.json` — plain HTML/CSS/JS.

## Architecture

- **Storefront**: `index.html`. CSS/JS are NOT loaded via static `<link>`/`<script>` tags — they're injected by a small inline script that builds `code/css/*.css?v=<version>` and `code/js/*.js?v=<version>` tags at runtime (see the two loader IIFEs near the top and bottom of `index.html`). The version comes from `localStorage.expert_asset_v`, synced against `expert_settings.asset_version` in Supabase (bumped by the admin's "Flush Cache" button, not by git pushes).
- **Admin panel**: `admin/index.html` + `admin/css/` + `admin/js/` — a separate static app with its own asset loading, unaffected by anything under the root `code/` folder.
- **Product pages**: `/product/<slug>.html` are AUTO-GENERATED by `scripts/generate-product-pages.js` from live Supabase data. Never hand-edit files under `product/` or `sitemap.xml` — `.github/workflows/generate-seo.yml` regenerates and overwrites them on every push to `main` (except pushes that only touch `product/**`/`sitemap.xml`, to avoid a loop) and nightly at 03:17 UTC.
- **Backend**: Supabase project `qhebhvllkovfbkqrcnmm` ("Experts Hardware"). Tables are prefixed `expert_*` (catalog/site data) and `offer_*` (email subscribers/campaigns). The anon/publishable key is baked into `code/js/01-config-data.js` as `SB_KEY` (base64-wrapped, not a secret — it's the public key, fine to reuse in one-off scripts).
- **Admin auth**: the 4 login types (owner `ultimate15`, manager `expert15`, admin `expert`, and "Team Accounts" created in Owner Controls) are real Supabase Auth users — `doLogin()` in `admin/js/03-auth.js` calls `/auth/v1/token?grant_type=password` directly (a synthetic email is derived from the username: `<username>@expert-admin.internal`). RLS on every admin-write table (`expert_products`, `expert_stock`, `expert_photos`, `expert_hidden`, `expert_banners`, `expert_cat_bgs`, `expert_settings`) only allows writes from `authenticated` + `is_admin(auth.uid())` — the public anon key can only `select`. `is_admin()` checks a row in `expert_admin_profiles` (id = the Supabase Auth user's uuid; role/permissions/display_name live there, not in the old `expert_admin_accounts`/`expert_admin_master` tables, which are dead — RLS-locked with zero policies, kept only as historical artifacts). Creating/editing/deleting an account (built-in or Team Account) goes through the `admin-manage-accounts` Edge Function (service-role-backed, since only the service role can create/delete Supabase Auth users) — never write `expert_admin_profiles` directly from the browser. After login, `SB_HDRS.Authorization` (defined once in `admin/js/01-core-data.js`) is mutated in place to the user's access token — every existing admin write already sends `SB_HDRS` as its headers, so that one mutation is what authenticates all of them; no per-call-site changes needed if you add a new write. The storefront's own stock write on checkout (`deductStock()` in `code/js/02-catalog-render.js`) goes through the `decrement_stock` RPC instead of a direct table write — that RPC is intentionally still anon-callable (real customers aren't logged in) but can only ever subtract, never set an arbitrary value.
- **Email**: `supabase/functions/send-offers` (Deno Edge Function) sends via Resend, gated by the `ADMIN_SEND_TOKEN` secret (`supabase secrets set`, never in git). The admin's Offers tab stores its copy of that token in that browser's `localStorage` only.
- **Images**: `expert-products/` is the main photo archive, organized by product-ID range folders (`1-50/`, `101-150/`, etc.) plus a few named subfolders (`big-red/`, `cant-find-products/`, `marhaba-products/`, `cat-images/`). `Bahar-Products/SKU-####.jpg` is the fallback for the original 60 hardcoded base products (via the `UL(id)` helper in `code/js/01-config-data.js`).

## Hard-won gotchas

- **Before renaming/moving any image folder, check whether `expert_photos.img_url` or `expert_products.img_url` store an ABSOLUTE URL pointing at it** (e.g. `https://mukarramkebra.github.io/Hardware-Website/expert-products/...`). A folder can look completely unreferenced in the codebase (grep for it in `.js`/`.html`) while still being referenced hundreds of times in the database. Renaming without checking has broken live product images twice in one session. Query first:
  ```sql
  select count(*) from expert_photos where img_url ilike '%<old-folder-name>%';
  select count(*) from expert_products where img_url ilike '%<old-folder-name>%';
  ```
- **CSS `url()` references are relative to the CSS file's own path.** Moving a CSS file to a different folder depth silently breaks any `url('../something.png')` inside it. Test locally (check Network tab / console for 404s) before pushing — and when you fix it, make sure the fix is actually staged (`git status`/`git diff --cached`) before committing. A `git mv` followed by a later `Edit` to the same file does NOT re-stage the edit automatically.
- **PostgREST upsert (`?on_conflict=col` + `Prefer: resolution=ignore-duplicates`) fails under RLS on any table where the calling role has no SELECT policy.** Postgres needs read visibility to evaluate the `ON CONFLICT` target; without it you get a `42501 row-level-security` error on every insert, even ones that aren't duplicates. If a table is intentionally insert-only for `anon` (e.g. `offer_subscribers` — subscriber emails/unsubscribe tokens shouldn't be publicly readable), do a plain `INSERT` and treat the resulting `409` as "already exists" client-side instead of using `on_conflict`.
- **Don't `git add -A` / `git add .`.** This repo tends to have pre-existing, unrelated dirty state in the working tree (things like a `product-images/` deletion the user did on purpose, or scratch folders) that shouldn't get swept into an unrelated commit. Stage explicit paths.
- **`git push` to `main` can get rejected as diverged** because `generate-seo.yml` may have committed a regeneration in the meantime. Recover with `git fetch && git merge origin/main --no-edit` (merge, not rebase — avoids rewriting commits already pushed) then push again.
- **Two separate hardcoded category lists must both be updated when adding a storefront category**: `CAT_DEFS` in `admin/js/05-categories.js` (Categories tab, has icon/default image) and `DEFAULT_CATS` in `admin/js/01-core-data.js` (dropdowns/filters, label only) — plus the actual tile/pill markup in `index.html`. None of these derive automatically from product data.
- **Category renames/reorders are cached to `localStorage`** (`cat_order_cache`, `cat_labels_cache`) so the page can paint the saved state synchronously before the async Supabase fetch resolves — otherwise a renamed category flashes its old name on every load. If you add another admin-editable category property, mirror this pattern (write the cache both on the storefront's own load, in `code/js/01-config-data.js`, AND immediately on save in `admin/js/05-categories.js`'s `saveCatChanges()`, since admin and storefront share one `localStorage` per browser).
- **Never enter the admin panel password**, even if it's handed over directly and the user asks — log in and check things yourself, or ask them to relay specific screens/values.
- **`create or replace function` does NOT replace a function whose parameter list changed** — Postgres identifies a function by name *and* argument types, so `admin_delete_order(p_id uuid)` and the old `admin_delete_order(p_token text, p_id uuid)` are different, coexisting functions; the old (possibly-vulnerable) one keeps working right alongside the new one until you explicitly `drop function old_name(old_arg_types)`. Check `select proname, pg_get_function_identity_arguments(oid) from pg_proc where proname = '...'` after any RPC signature change to confirm the old overload is actually gone.
- **A newly created Postgres function grants `EXECUTE` to the `PUBLIC` pseudo-role by default**, and every role (including `anon`) implicitly inherits from `PUBLIC` — so `revoke execute on function f() from anon` alone does NOT stop `anon` from calling it if `PUBLIC` still has the grant. Confirm with `select grantee, privilege_type from information_schema.routine_privileges where routine_name = '...'` and `revoke ... from public` explicitly (then re-grant to the specific roles that should keep access) if a function is meant to be restricted.

## Data patterns worth knowing

- Per-product extras that aren't real columns (SKU override, brand, SEO keywords, size/pack variants, min/max order qty) live as JSON blobs in `expert_settings`, keyed by product ID — see `sku_map`, `brand_map`, `product_keywords`, `product_variants`, `qty_limits`.
- Product photos: `expert_products.img_url` is meant for cheap plain http(s) links only (never base64 — that column gets fetched on every visitor's page load). Actual uploaded/base64 photos live in `expert_photos`, keyed by `product_id`, checked first by the storefront.
- Featured/sale data lives in `expert_settings` key `featured_offers` as an ORDERED array of `{id, sale}` — array order is the homepage ticker's display order. Read-modify-write it; don't reconstruct it from scratch or you'll lose the curated order.
- Deleted products go to a 60-day-retention client-side trash (`localStorage.jain_deleted`), not a real soft-delete column — see `admin/js/09-deleted.js`.
- Admin action history (`localStorage.jain_audit_log`, Owner Controls tab) is per-browser, not synced via Supabase — an action taken on one device won't show in another device's log.

## Workflow notes

- No test suite. Verification is: local static server (`.claude/launch.json`, `local-static`) + browser console/network checks for anything visual/interactive, then push, then poll the live GitHub Pages URLs with `curl` to confirm the deploy actually landed (GitHub Pages + the SEO Action both take a minute or two).
- One-off maintenance scripts live in `scripts/` (`fix-*.js`, `add-*.js`, `consolidate-*.js`, etc.) — plain Node, no dependencies, just built-in `fetch`/`fs`. Always give write scripts a `--dry-run` flag and run it first.
